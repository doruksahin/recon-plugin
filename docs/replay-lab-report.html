Measure the ticket twice. Change the skill once.

The laboratory freezes a real Jira task and its codebase, hides the expected decisions from the agent, and scores the retained triage. Its intention is not to make ATT-4845 look solved. Its intention is to make a future skill-quality claim falsifiable.

02 · Execution

One run path, two LLM contexts

State and mutation stay on rails. The operator explains and hands off; only the clean replay context performs semantic triage.

1 · PrepareOperator validates, freezes exact inputs, excludes the oracle, then derives PREPARED.
2 · ExplainOperator reports what is frozen, excluded, writable, and forbidden.
3 · Hand off + stopCopy-ready prompt sends only the run path to a genuinely fresh context.
4 · Generate + verify + returnReplay LLM writes submission/triage.yaml, runs the bundled verifier clean, returns the run path, and stops.
5 · Derive + evaluateOperator derives SUBMITTED; evaluate verifies, scores, and retains two artifacts once.
6 · Explain + actSCORED output names result, evidence boundary, artifact paths, and exact next action.
Why this order: the operator context can prepare and later interpret an oracle-backed score, but it is contaminated for generation. The fresh context can generate, but cannot evaluate itself. The run directory reconnects them without sharing chat history. R14R15R17
03 · LLM handoff

A follow-up another LLM can actually execute

A good handoff answers four questions: what happened, where is the evidence, what happens next, and when must this context stop.

Before: chat history was hidden state

The operator had to remember the case path, whether generation finished, which score command to run, and where terminal output went. A new LLM received a narrative and reconstructed progress.

Failure mode: the operator context could accidentally author the submission, the returning context could omit the case, or scoring could be rerun and lose the original trace.

After: the run directory is the handle

state <run> derives PREPARED, SUBMITTED, or SCORED from validated files. It prints the exact next command. evaluate writes the human trace and machine result once.

Handoff: pass one absolute run path. Any project LLM can resume without reading the prior conversation. R14R17

07 · Scoring

Why one blocker cannot earn two decisions

Signal matching creates candidate edges. Maximum bipartite matching then assigns each decision to at most one blocker and each blocker to at most one decision. R3R6

Open decision A
Open decision B
↘
↗
One blocker
Result: the production verifier rejects the candidate before scoring because one blocker cannot map to two independently answerable OPEN decisions.
Known limitation: the case oracle remains lexical and case-specific. A valid unseen synonym may false-fail; an agent with oracle access could keyword-stuff. The closure rail prevents structural ambiguity, not semantic overfitting. Independent review remains required.

09 · Concrete scenarios

What different outcomes mean

The lab separates handoff, mechanism, and generative-quality failures so the next action is specific.

Scenario A — the user returns only a run path.
Run state <run>. The receipt derives the case; SUBMITTED prints the exact evaluate command. Prior chat is unnecessary.
Scenario B — the fresh LLM has not written a submission.
State remains PREPARED. Reissue the clean-context handoff and stop; the operator must not fill the missing YAML.
Scenario C — candidate fails its bundled verifier.
evaluate exits 2 without retaining a score or decision coverage. Return the fresh context to the exact verifier command; do not call this a quality result.
Scenario D — disposition is wrong.
Artifact is valid, but expected BLOCKED differs. Investigate the six triage checks before blocker wording.
Scenario E — merged OPEN decisions.
The artifact verifier rejects the candidate. Split the independently answerable decisions before it can enter scoring.
Scenario F — full coverage in one run only.
Promising but not stable. Repeat in fresh contexts; do not call the shipped skill improved from one sample.
Scenario G — evaluation is already SCORED.
Read the retained JSON and trace. Never rerun or revise evaluation; start another run for another sample.
Scenario H — synonym judged valid by a reviewer.
Amend the oracle through review, rerender this report, and retain why the rubric changed. Do not hand-edit a score.
10 · Decision record

What I chose—and what I refused to claim

The architecture follows the repository’s outcome-first behavior contract rather than optimizing for a persuasive demo.

Decisions and reasoning

  • Instrument before skill edit: otherwise baseline and fix are designed together.
  • Real ticket, pre-comment: observed origin without answer leakage.
  • Full target commit: code evidence remains inspectable while the current dirty branch is irrelevant.
  • Production verifier first: quality scores never legitimize invalid Recon output.
  • Replay-only owner map: offline preparation supplies explicit non-Jira tokens instead of guessing an account ID.
  • One-to-one matching: decision atomicity becomes a mechanical property.
  • Repository-local operator skill: LLMs receive the same routing and handoff contract without shipping internal oracles in the plugin.
  • Run path as single handle: receipt-derived state replaces conversation memory and evaluation preserves its own integrity links.
  • Generated HTML: explanation is a checked view, not a drifting parallel specification.

Explicit non-claims

  • No fresh-context model baseline has yet been recorded.
  • No shipped Recon SKILL.md generative behavior was changed or proven better in this milestone.
  • Fixtures prove scorer properties, not generative quality.
  • The local operator skill validates structurally, but activation quality is not yet forward-tested across model tiers.
  • The offline verifier does not test activation, live Jira transport, visual repro, or delivery.
  • One ambiguous BLOCKED ticket does not establish “works for any task.”
  • Filesystem isolation is procedural; a fully unrestricted agent could inspect the source repository.
Next accountable move: use the new handoff to run the current clean plugin revision three times from this prepared state, retain every submission and evaluation, then revise the shipped triage skill only if the failure reproduces. Add READY and NEEDS_INFO cases before a general quality claim. R9R12R16
